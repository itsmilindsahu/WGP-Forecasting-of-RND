# Codebase guide

One-line purpose for every file that matters, in pipeline order. Each stage
folder maps to one step: chain → IV curve → RND → kernel → GP → baselines →
scoring → write-up.

## Entry points (repo root)

| File | Purpose |
|---|---|
| `run_all.py` | Runs the whole pipeline (stages 1→7) on **synthetic** data. No network or data file needed — start here. |
| `run_all_real.py` | Same pipeline, but on the **real** Deribit chain built by `01_data_collection/build_real_chain.py`. Needs `--tick-csv-gz <path>`. |
| `requirements.txt` | Python deps. |
| `README.md` | Project narrative: what this is, results table, dev log. Read this first for *why*; use this guide for *where*. |

## `01_data_collection/` — get an option chain, fit a smooth IV curve

| File | Purpose |
|---|---|
| `simulate_data.py` | Synthetic multi-day option-chain generator (SVI smile + random walk). No network. Used by `run_all.py`. |
| `fetch_deribit.py` | Real Deribit public-API client. Needs live network (not available in this sandbox). |
| `fetch_yfinance.py` | Real Yahoo Finance client via `yfinance`. Same network caveat. |
| `build_real_chain.py` | Turns a **historical Deribit tick-level export** into the same schema `simulate_data.py` produces, so nothing downstream changes. This is what `run_all_real.py` actually uses in place of live fetching. Its docstring explains the BTC/expiry/binning choices. |
| `fit_iv_curve.py` | Fits the raw-SVI implied-variance curve per day by least squares. Output feeds stage 2 (Breeden–Litzenberger needs a smooth curve, not raw ticks). |
| `data/` | Generated CSVs (`option_chains.csv`, `iv_curves.csv`, `svi_params.csv`). Gitignore-able; regenerated by the run scripts. |

## `02_rnd_extraction/` — turn the IV curve into a risk-neutral density

| File | Purpose |
|---|---|
| `breeden_litzenberger.py` | Applies Breeden–Litzenberger (2nd derivative of the call-price curve) to extract each day's RND, plus `martingale_check()` (extracted mean vs. forward, per-day audit). |
| `data/` | `rnd_curves.csv` (one row per date × strike) and `martingale_diagnostics.csv`. |

## `03_wasserstein_kernel/` — distribution-input kernel for the GP

| File | Purpose |
|---|---|
| `wasserstein_kernel.py` | Closed-form 1D W2 distance via quantile functions, and the Gaussian-Wasserstein kernel `k(F,G) = exp(-γ·W2²)` built on top of it (Bachoc et al. 2018 construction). This is the one file the whole "distribution-valued GP input" idea rests on. |
| `test_synthetic.py` | Checks the closed-form W2 against known Gaussian-pair formula, and that the resulting kernel matrix is PSD. Run this in isolation if you ever touch `wasserstein_kernel.py`. |
| `gram_matrix.csv` | Cached kernel matrix from the last full run. |

## `04_gp_model/` — the actual forecasting model

| File | Purpose |
|---|---|
| `fit_gp.py` | `WassersteinGP`: MLE (via Cholesky) + posterior predictive for `RND_t → Var(RND_{t+1})`. Also `WassersteinBarycenterForecaster`, which forecasts the **full next-day density** (Nadaraya–Watson quantile barycenter), used only in stage 6's full-density metric. |
| `results/` | `predictions.csv`, `summary.txt` (fitted hyperparameters + held-out RMSE/coverage). |

## `05_baselines/` — what the GP has to beat

| File | Purpose |
|---|---|
| `linear_baseline.py` | Collapses each RND to (mean, variance, skew) and fits OLS → next-day variance. Also produces a moment-matched Gaussian as its "guess" at the full next-day density. |
| `persistence_baseline.py` | Pure random-walk null: tomorrow = today. Both a scalar and a full-density version. This is the one every other model actually has to beat. |
| `results/` | Predictions from both baselines. |

## `06_evaluation/` — score everything on the same held-out days

| File | Purpose |
|---|---|
| `evaluate.py` | Computes coverage, NLPD, and full-density W2 error for GP vs. linear baseline vs. persistence, plus a no-forecast Gaussian floor and a shape-only (mean-removed) W2 diagnostic. This is what the README's results table comes from. |
| `results/` | `comparison_per_day.csv`, `comparison_summary.csv`, `comparison_plot.png`. |

## `07_writeup/` — communicate the result

| File | Purpose |
|---|---|
| `build_demo.py` | Reads stage-6 CSVs, embeds them as JSON into a single self-contained `docs/index.html` (Chart.js via CDN). |
| `docs/index.html` | The interactive demo itself — open directly or serve via GitHub Pages pointed at `/docs`. |
| `results_memo.md` | The actual write-up: results, honest read of them, next steps. This is the "so what" document — read it after the README. |

## `archive/` — things kept for reference, not part of the live pipeline

| Path | Purpose |
|---|---|
| `synthetic_backup/` | Full snapshot of the pipeline's outputs *before* the switch to real data (the run with the four bugs Sven flagged, all fixed). Kept so the synthetic-vs-real comparison in the README is reproducible. Not touched by either run script. |
| `stale_root_artifacts/` | A duplicate `index.html` / `comparison_plot.png` that were sitting at the repo root — different (larger, self-styled) builds than the canonical ones in `07_writeup/docs/` and `06_evaluation/results/`, and not referenced by the README or any script. Moved here rather than deleted in case they were an intentional separate GitHub Pages root build; safe to delete if not. |

## What changed structurally (vs. the original upload)

- `dayN_*` folders → `0N_*` folders (same order, drops the diary framing — a
  fresh reader shouldn't need to know which calendar day something was built
  on to know what it does).
- Removed committed `__pycache__/` directories and added a `.gitignore` so
  they don't come back.
- `_synthetic_backup/` → `archive/synthetic_backup/` — same content, now
  grouped under a single `archive/` root instead of sitting as a top-level
  folder next to the live pipeline.
- The two orphaned root-level `index.html` / `comparison_plot.png` moved to
  `archive/stale_root_artifacts/` (see above) instead of living at the repo
  root next to `README.md`.
- Every internal path reference (`sys.path.append(...)`, `to_csv(...)`,
  docstrings) was updated to match — `run_all.py` was re-run end-to-end
  against the new layout to confirm it still produces identical output.

Nothing about *how* the code works changed — same modules, same functions,
same data flow. This is a rename/reorganize pass only.
